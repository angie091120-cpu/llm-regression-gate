# Degradation design: the four E1 prompt versions

**Written 2026-09-14, before any E1 call was made.** Everything in the
"Predicted" blocks below is an expectation recorded in advance so that it can
be wrong in public. No E1 data existed when this file was committed; the
confirmatory tests it feeds are fixed in
[`PREREGISTRATION.md` section 10](PREREGISTRATION.md).

E1 asks one question: how large a prompt regression does a 70-case gate
actually catch? Answering it needs prompts that are worse in a specific,
nameable way. The four versions below each remove one thing a real team
removes -- to cut token cost, to "tidy up" a prompt, or because whoever wrote
the rule left the company -- and nothing else.

## How the files were built

`prompts/v2a.yaml` .. `prompts/v2d.yaml` were generated by slicing
`prompts/v1.yaml`'s own text, so every line that survives is byte-identical to
v1, down to where the lines wrap. Nothing was re-wrapped and nothing was
re-typed. Three fields differ by necessity (`version`, `created_at`, and a
three-line `#` comment at the top of each file naming the degradation); YAML
comments never reach the API. `model` stays `claude-haiku-4-5`.

| File | Edit | Prompt-content diff vs v1 | system_prompt chars | few-shot examples |
|------|------|---------------------------|---------------------|-------------------|
| `prompts/v1.yaml` | baseline | -- | 1,916 | 4 |
| `prompts/v2a.yaml` | few-shot 4 -> 2 | -8 / +0 lines | 1,916 (identical) | 2 (billing, technical) |
| `prompts/v2b.yaml` | few-shot 4 -> 0 | -17 / +1 lines | 1,916 (identical) | 0 |
| `prompts/v2c.yaml` | category definitions + tie-break rule removed | -15 / +3 lines | 1,017 | 4 (identical) |
| `prompts/v2d.yaml` | bilingual / typo / zhuyin / sarcasm paragraph removed | -5 / +1 lines | 1,580 | 4 (identical) |

Diff counts exclude the comment header and the `version` / `created_at`
fields. Verify with:

```bash
norm() { grep -v '^#' "$1" | grep -v '^version:' | grep -v '^created_at:'; }
diff <(norm prompts/v1.yaml) <(norm prompts/v2c.yaml)
```

Each file passes `classifier.load_prompt_config()` unchanged -- that is what
makes a prompt swap a config change instead of a code change, and it is why
E1 needs no edit to `classifier.py`, `evalkit/` or `golden_dataset.json`.

## One case is inside the v1 prompt (disclosed, not fixed)

Few-shot example 4 of v1 is `"Cool, another outage. Love it."` with the label
`general`. That is **case-043 of `golden_dataset.json`, verbatim** -- the same
string, the same gold label. The baseline prompt therefore leaks one of the 70
evaluation labels into its own context.

Two consequences, both of which belong in any write-up:

1. v1's 64/70 is optimistic by at most one case. In fact it is not optimistic
   at all here: across five E0 runs the classifier answered `technical` on
   case-043 every single time, contradicting a label sitting verbatim in its
   own prompt (`experiments/results/tables/per_case_instability.csv`).
2. v2a and v2b remove that example, so for those two versions the prompt edit
   and the removal of the leak are confounded. `PREREGISTRATION.md` section 10
   pre-specifies the sensitivity analysis: H1 and H2 are re-run with case-043
   dropped (n = 69), reported next to the primary result whichever way it
   comes out. v2c and v2d keep all four examples and are unaffected.

The leak was found on 2026-09-14 while building these files, after E0 had
already run. The dataset is frozen for the study (`PREREGISTRATION.md`
section 2), so case-043 stays where it is and this paragraph is the fix.

## v2a -- few-shot examples 4 -> 2

**Removed.** The `account` example (`我忘記密碼了，點忘記密碼的信件一直沒收到…`)
and the `general` example (`Cool, another outage. Love it.`). The billing and
technical examples stay, byte-identical. `system_prompt` is untouched.

**Why a real team does this.** The four examples are roughly 450 of the ~1,690
input tokens on every classifier call. Halving them is the first thing anyone
proposes when a triage prompt runs at volume, and "we kept one example per
major category" is how it gets justified in review. The two categories that
survive here are the two a B2B help desk sees most.

**Predicted (not measured).**

- At risk: the 16 `account` and 17 `general` cases; the model keeps the written
  definitions for both but loses the demonstration.
- Sharpest within that: the four `general` + `edge` cases (case-012, case-020,
  case-043, case-055). All four already fail under v1, so the *measurable*
  movement has to come from `general` + `easy` (12 cases) and `account` +
  `easy` (13 cases), which v1 gets right today.
- The removed `general` example is also v1's only sarcasm demonstration, so
  the four sarcasm cases (case-012, case-020, case-043, case-068) are a named
  at-risk subset even though the sarcasm *instruction* survives in the system
  prompt.
- Expected size: the smallest of the four versions on `category_match`. The
  definitions and the tie-break rule both survive, so the model still has the
  decision rules -- it only loses two worked examples.
- Direction on `passed` (secondary): the surviving examples still show one
  Chinese and one English summary, so summary-language drift is predicted to
  be small.

## v2b -- few-shot examples 4 -> 0 (zero-shot)

**Removed.** All four examples; `few_shot_examples: []`. `system_prompt` is
untouched.

**Why a real team does this.** Same cost pressure as v2a taken to its
conclusion, usually with the argument that "the instructions already say
everything the examples show". It is also what happens accidentally when a
prompt is ported to a new framework and the example block is not carried over.

**Predicted (not measured).**

- Largest `category_match` drop of the four versions.
- At risk across every stratum, concentrated in the 17 `ambiguous` and 8
  `edge` cases, where the examples were doing the work the prose cannot.
- The `general` category (17 cases) is defined in v1 as a residual class
  ("anything that isn't clearly billing/technical/account"). Predicted to
  absorb fewer cases without a demonstration, so `general` recall falls while
  `technical` false positives rise -- the confusion direction E0 already shows
  on case-012, case-043 and case-055.
- Secondary metric `passed` predicted to fall further than `category_match`:
  both Chinese-language summary demonstrations are gone, so summaries for the
  35 zh-tw and 7 mixed cases may come back in English while the judge's
  reference summary is in Chinese. The `passed` - `category_match` gap is the
  number to look at, not `passed` alone.
- The v1 leak on case-043 disappears here; see the sensitivity analysis above.

## v2c -- category definitions and the tie-break rule removed

**Removed.** Two things, both decision rules rather than examples:

1. The nine lines that enumerate each category's scope (billing's
   "currency/exchange-rate questions", technical's "exports, mobile app
   issues", account's "SSO/2FA setup", general's "compliance/SOC2 questions,
   thank-you notes, vague complaints"). The lead-in line keeps the label set:
   `Classify each email into exactly one category: billing, technical, account
   or general.` -- six words that are not in v1 and are there to keep the
   sentence grammatical without re-introducing any definition.
2. The tie-break sentence: *"If an email could plausibly fit two categories,
   pick the one that reflects what the customer needs actioned first (e.g. …
   -- use judgment)."*

Few-shot examples are byte-identical to v1.

**Why a real team does this.** Both edits are the standard "the model already
knows what billing means" cleanup, done when a prompt is shortened for a
cheaper model or when the person who wrote the enumeration leaves and nobody
dares own it. The tie-break rule in particular reads like boilerplate until
you find the cases it decides.

**Predicted (not measured), and this one is predicted to cut both ways.**

- Down: the 17 `ambiguous` cases, which are exactly the ones the tie-break
  rule was written for -- the explicit cross-category ones are case-003,
  case-009, case-031, case-033, case-038, case-052, case-070.
- Down: cases that hinge on one enumerated phrase. The four currency cases
  (case-017, case-020, case-048, case-068) lose billing's
  "currency/exchange-rate questions"; the five export/sync cases (case-006,
  case-014, case-030, case-045, case-069) lose technical's "exports, data sync
  issues"; case-055 and case-012 lose general's "vague complaints".
- **Up**: two specific cases where v1's own rules point the wrong way.
  - case-018 (zh-tw, easy, gold `technical`) is an SSO domain-verification
    failure. v1 lists "SSO/2FA setup" under `account`, and v1 answers
    `account` on all five E0 runs. Deleting the enumeration removes the pull.
  - case-009 (zh-tw, ambiguous, gold `billing`) is a failed card charge that
    downgraded the account. v1's tie-break example is almost the same
    scenario and resolves it to account-access; v1 answers `account` on all
    five E0 runs. Deleting the tie-break removes that anchor.
- So b and c (the two discordant cells of the McNemar table) are both
  predicted to be non-zero for v2c, and the risk difference may be small while
  the underlying churn is not. `experiments/results/tables/e1_main.csv`
  reports b and c separately for this reason; a near-zero RD on this version
  is a finding, not a null.

## v2d -- bilingual / typo / zhuyin / sarcasm handling removed

**Removed.** Five lines: *"Emails may be written in Traditional Chinese,
English, or a mix of both (common in Taiwanese tech workplaces). They may
contain typos, informal shorthand (including zhuyin fragments like "ㄓㄨㄥ" for
"中"), sarcasm, or be only a single short sentence. Classify based on the
underlying intent, not the language or politeness of the wording."* The
tie-break rule that shared a line with it survives, at v1's original line
breaks. Category definitions and all four examples are byte-identical to v1.

**Why a real team does this.** This paragraph is the one an English-speaking
reviewer deletes as "obvious" or as locale-specific clutter, and the one a
prompt-translation pass drops on the floor. It is also the only part of v1
that is specific to the market the fictional product sells into, which makes
it the most likely casualty of a template rewrite.

**Predicted (not measured).**

- At risk: the 35 zh-tw and 7 mixed cases; the 28 en cases are predicted to be
  nearly unaffected on `category_match`.
- Named subsets: the one zhuyin/typo case (case-034, `ㄓㄨㄥ` and `我門`), the
  four sarcasm cases (case-012, case-020, case-043, case-068), and the three
  single-sentence cases (case-012, case-025, case-043).
- Expected size: small on `category_match`, because the four examples still
  demonstrate a sarcastic email resolving to `general` and a Chinese email
  resolving to `billing`. If the effect is near zero, the reading is that the
  examples were carrying the rule -- which is a useful thing for a gate design
  to know, and is the reason v2d is worth a confirmatory slot rather than
  being folded into v2c.
- The language strata are small (7 mixed cases, 8 edge cases), so a
  stratum-level Wilson interval here is roughly +/- 30 percentage points. Any
  stratified reading of v2d is exploratory by construction
  (`PREREGISTRATION.md` sections 4 and 8).

## What this design cannot tell you

These four edits are chosen by the author, not sampled from real prompt
regressions. Effect sizes measured here describe these four interventions on
these 70 cases; how they map onto the ways a production prompt actually decays
is unknown, and `PREREGISTRATION.md` section 8.4 says so in the terms the
write-up has to use.
